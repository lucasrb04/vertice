# Deploy (pipeline e produção na OCI) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Todo push em `main` que passe em lint, tipos, testes com 90% de cobertura e nas varreduras de vulnerabilidade publica sozinho o Vértice em `https://verticehub.online`, com migrations antes do app e rollback automático.

**Architecture:** GitHub Actions roda `verify` e `dependencies` em paralelo, depois `image` (build nativo ARM, Trivy e push no GHCR) e, só em `main`, `deploy`. O deploy é um SSH com chave presa a `/opt/vertice/bin/deploy.sh`, que recebe apenas a tag (SHA) e faz migrate → app → verificação → rebuild da busca. Na VM rodam `postgres`, `app` e `caddy` via `deploy/compose.prod.yml`; a imagem `migrate` carrega os arquivos de `deploy/` para a VM.

**Tech Stack:** GitHub Actions (`ubuntu-24.04-arm`), Docker multi-stage (`node:22-alpine`), GHCR, Trivy, Caddy 2, Postgres 16, Vitest + `@vitest/coverage-v8`, bash.

**Spec:** `docs/superpowers/specs/2026-11-04-deploy-design.md`

## Global Constraints

- Domínio de produção: `verticehub.online` desde o primeiro deploy. **Sem `sslip.io`** (substitui §5.7 da spec).
- pnpm com `corepack` e `--frozen-lockfile` (D30). Node 22 nas imagens (`engines >=22.9`).
- Imagens `linux/arm64`, build no runner `ubuntu-24.04-arm`, sem emulação.
- Registro: `ghcr.io/lucasrb04/vertice-app:<sha>` e `ghcr.io/lucasrb04/vertice-migrate:<sha>`, pacotes públicos.
- Nenhum segredo na imagem, no repositório ou em log. `NEXT_PUBLIC_*` entram como build args vindos de Variables do GitHub.
- **Segredos de runtime moram só no Environment `production` do GitHub.** A cada deploy o job monta o `.env` e o envia pelo stdin do SSH; o `deploy.sh` valida e grava `/opt/vertice/.env` (600). Ninguém edita o `.env` da VM à mão (substitui §5.4 da spec nesse ponto).
- `pull_request`, nunca `pull_request_target`. `permissions` mínimas por job; só `image` em push para `main` ganha `packages: write`.
- Portões: cobertura ≥ 90% em linhas, funções, branches e statements; `pnpm audit --prod --audit-level high`; Trivy `severity: HIGH,CRITICAL`, `ignore-unfixed: true`, `exit-code: 1`.
- Só 22, 80 e 443 abertas; Postgres e a porta 3000 nunca publicados.
- Caddy **sobrescreve** `X-Forwarded-For` com `{remote_host}` (D44).
- `app` com uma réplica (D22). Migrations seguem aditivas.
- Textos, comentários e mensagens de commit em pt-BR. Sem `pkill` amplo.

## Review Focus

1. Primeiro deploy, sem `/opt/vertice/RELEASE`: se a verificação falhar, não há versão anterior; o script deve sair com erro claro em vez de tentar subir uma tag vazia.
2. Dois pushes seguidos em `main`: o segundo deploy espera o primeiro terminar (nunca cancela no meio de uma migration).
3. `SSH_ORIGINAL_COMMAND` malicioso (`abc; rm -rf /`, vazio, SHA com espaço): recusado antes de qualquer comando `docker`.
4. Migration falha: o app antigo continua no ar, `RELEASE` não muda e o job fica vermelho.
5. VM reinicia: `postgres`, `app` e `caddy` voltam sozinhos e os dados e certificados persistem em volumes nomeados.
